# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

pplz is a personal contact manager (Mac, iPhone, iPad) that enriches Apple Contacts with a history of meetings, calls, events and photos. `README.md` describes the product and the full CLI, `SPEC.md` the design, `DECISIONS.md` the decisions taken during autonomous runs.

## Commands

Needs full Xcode (the Command Line Tools alone cannot build SwiftData models). There is no linter.

```sh
swift build                                   # core, UI and CLI
swift test                                    # all tests
swift test --filter NotesBlockTests           # one suite
swift test --filter NotesBlockTests/noHistoryMeansNoBlock   # one test
swift build -c release                        # the binary a `pplz` symlink on the PATH points to

scripts/build-app.sh mac                      # builds pplz.app and installs it in /Applications
scripts/build-app.sh simulator                # iOS simulator build
scripts/build-app.sh iphone "<device name>"   # build and install on a connected, unlocked device
```

- Commit and push only when the user says so, or in an `/autonomous` run. Do not create or switch a branch without the user's permission.
- The Xcode project, the Info.plists and the entitlements in `App/` are generated by XcodeGen and not committed. Edit `App/project.yml`; both scripts run `xcodegen generate` themselves. `App/Local.xcconfig` (team ID, not committed) must exist.
- `scripts/ui.sh "<app args, | separated>" "<steps, ; separated>" [simulator]` clicks through the iOS app in a simulator and writes screenshots and accessibility trees to `tmp/ui/`. Steps: `tap:<label|identifier|placeholder>`, `type:<text>`, `clear`, `swipeUp`, `swipeDown`, `back`, `wait:<seconds>`, `screenshot:<name>`, `tree:<name>` (`App/UITests/ScriptRunnerTests.swift`). It always starts the app with `-noSync YES`.

## Do not touch the user's real data

The default store (`~/Library/Application Support/pplz/pplz.store`) is the user's real data and syncs through iCloud; the address book is real too.

- Every manual CLI run gets `--store <temp file> --no-contacts` **on the command itself**. Do not rely on an `export PPLZ_STORE=…` earlier in a `&&` chain: if an earlier step fails, the export never runs and the command writes to the real store.
- Launch the app for a check with `-store <temp file>` (and `-noContacts YES` where contacts are not needed).
- Opening a store with a newer build migrates it in place. Open `Tests/PplzCoreTests/Fixtures/before-photos.store` only through a copy; a test checks that the original still has the old schema.
- After a change to the data model, rebuild the release binary, so that an old `pplz` on the PATH does not open the store.
- `geocache.json` (the hourly geocoding budget) sits next to the default store and does not follow `PPLZ_STORE`.
- The repository is public: nothing from `private/` and no real person's data goes into code, fixtures, commits or docs.

## Browser checks with the Playwright MCP

All output of the Playwright MCP stays in `tmp/playwright/` (`tmp/` is not committed): screenshots, page snapshots, console logs, traces, downloads and the browser profile.

- `.mcp.json` starts the server with `tmp/playwright` as its output directory. Do not start a different Playwright server for this repository.
- Give each file that you name a path in that directory, for example `tmp/playwright/map-pins.png`. Do not write to the repository root or to `.playwright-mcp/`.

## Architecture

Swift 6 package with three targets, plus the apps in `App/`:

- **PplzCore** — model, store, Contacts and calendar access, capture (Vision, on-device language model), geocoding. No UI.
- **PplzUI** — the SwiftUI screens shared by the Mac and the iOS / iPadOS app. The app targets in `App/Mac` and `App/iOS` are only an entry point each.
- **pplz** — the command line (`Sources/pplz/Pplz.swift`, swift-argument-parser), Mac only.
- **Share extensions** (`App/Share`, `App/ShareMac`, `App/ShareCommon`) only deliver a screenshot or link into an App Group inbox (`CaptureInbox`); the app does the reading and asking.

### Store

- `PplzStore` is a plain class (no actor) around one `ModelContext` with autosave off: every mutator saves itself, multi-step writes go through `atomically {}`, which rolls back on error.
- The `@Model` classes in `Model.swift` are internal. Callers get snapshots and records, never model objects.
- CloudKit rules for the model (header of `Model.swift`, SPEC §8.2/§8.3): every attribute has a default or is optional, every relationship is optional and has an inverse, no unique constraints, additive changes only. There is no versioned schema or migration plan; the store relies on lightweight migration, guarded by the fixture test in `PhotoTests.swift`.
- App and CLI share one store file. Only the apps sync with CloudKit, and only their default store; the CLI, the tests and a store given with `-store` / `--store` never sync.

### Contacts

- pplz never imports contacts: `PeopleDirectory.merge` joins the live address book with the pplz persons on every load.
- Identity is the `pplz://person/<uuid>` URL row in the contact (`PersonLink`), then the stored local contact identifier, which differs on every device. A name never decides a match.
- Contacts access is a set of caseless enums with static functions; there is no protocol and no fake. Logic is kept testable by splitting **planning** (pure: `ContactsSync.historyPlan` / `linkPlan`, `ContactMirror`, `NotesBlock`, `ContactEdit`) from **applying**.
- Writes go two ways. On the Mac a contact that has a note cannot be saved through `CNContactStore` without Apple's notes entitlement (SPEC R1), so writes go through the Contacts app by AppleScript (`ContactsApp`); iOS / iPadOS writes directly (`SystemContacts`). Relationships and the history block are written by the Mac only.
- pplz owns only what it wrote: the `pplz` link row, related-name rows recorded in `ContactJournal` (append-only JSONL), and the note block between `── pplz ──` and `── /pplz ──`. Text around the block is never changed, and note text never leaves the device.

### UI

- `PeopleModel` is the one `@MainActor @Observable` view model. It owns the store and opens it lazily; views get the model and never see the store.
- Platform differences are mostly `#if os(macOS)` blocks inside the shared files.
- Launch arguments (`-key value`), useful for checks and used by `scripts/ui.sh`: `-store <file>`, `-noContacts YES`, `-noSync YES`, `-forceSync YES`, `-select <name|id>`, `-show log|quickLog|edit|editEvent|connect|editContact|newContact`, `-mode events|map`, `-capture <image file>`.

### CLI

Every subcommand takes the `Common` option group (`--store`, `--no-contacts`, `--json`). Output goes through `common.emit(_:text:)`; failures go through `attempt {}` / `attemptAsync {}`, which print to stderr and exit with code 2.

## Tests

- Swift Testing (`@Suite`, `@Test`, `#expect`); XCTest only in `App/UITests`.
- Each test opens a real store in a temporary file with `makeStore()` (`StoreTests.swift`). UI-model tests build `PeopleModel(configuration: .init(storeURL:, usesContacts: false))`.
- No test touches the address book: Contacts behaviour is tested through the pure planning functions.

### TDD workflow

Adapted from [TDD with Claude Code](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/workflows/tdd-with-claude.md). Red → green → refactor, one behaviour per cycle:

1. **Red** — write the failing test first and no implementation. Run it and see it fail for the expected reason (the function is missing, or the behaviour is wrong), not because of a typo.
2. **Green** — write the minimum code that makes it pass, nothing more.
3. **Refactor** — clean up while the tests stay green; run them after each change.

- Arrange-Act-Assert, one behaviour per test where possible, and a name that states the behaviour, in the style of the existing tests (`noHistoryMeansNoBlock`, `showsAtMostTenEventsButCountsAll`).
- Do not write tests after the fact that merely confirm what the implementation does.
- **Changing existing code that lacks tests:** first pin its current behaviour with characterization tests, odd outputs included, in a step of their own. From then on those tests are read-only: if one looks wrong during the refactor, stop and report it instead of editing it.
- **No verification gap:** never report something done before the checks ran and their output was read. All layers must pass: `swift test`, and for behaviour a user sees, an end-to-end check as well — the CLI against a temporary store, or the app through `scripts/ui.sh` / a launch with `-store`. Passing unit tests do not prove an acceptance criterion that describes end-to-end behaviour.
- For a long task, have the result checked by something other than the session that wrote it (a fresh subagent or a review) before calling it done.

## Docs

- `SPEC.md` marks every statement **[S]** stated by the user, **[A]** assumption, **[?]** open. Code comments refer to its sections (`SPEC §8.3`, `R1`); keep both in step when behaviour changes.
- User-visible changes are described in `README.md` in the same change.
- Four documents, four jobs — do not mix them:

  | Document | Holds | Written by |
  |---|---|---|
  | `SPEC.md` | what pplz does and what is still assumed or open | any change of behaviour |
  | `GLOSSARY.md` | the project's words, one or two sentences each; no behaviour, no implementation | a grilling session (below) |
  | `docs/adr/NNNN-<slug>.md` | why a decision was taken, only if it is hard to reverse **and** surprising without context **and** a real trade-off | a grilling session, rarely |
  | `DECISIONS.md` | what Claude decided alone during an `/autonomous` run, for the user's review | `/autonomous` only |

  `GLOSSARY.md` and `docs/adr/` are created when the first term or decision is settled, not before.

## Writing

Write in ASD-STE100 Simplified Technical English. This applies to all prose: replies, docs, code comments, commit messages and issue text.

- Short sentences: 20 words at most in an instruction, 25 in a description. One instruction in each sentence.
- Active voice and simple tenses. Use the imperative for instructions.
- One word has one meaning, and one thing has one name. The project's technical names are the terms in `GLOSSARY.md`.
- No idioms, no slang, no filler.
- Paragraphs have one topic and six sentences at most.

## Planning a change: `/grill-with-docs`

The user starts it by typing `/grill-with-docs`; do not start it yourself. It is an interview about a plan, in rounds, that writes down the vocabulary and the hard decisions while it runs. The skill itself is one line that loads two others, so:

- Load **both** `grilling` (the interview) and `domain-modeling` (the writing), the copies in `.claude/skills/`, with the Skill tool before the first question. With only the first one the interview runs and nothing is written.
- **Start from `SPEC.md`:** the **[A]** and **[?]** items of the area, and the items of §9 "Still open", are the first questions. What `SPEC.md` or the code already answers is looked up (by a subagent), never asked.
- **Asking is the point here.** A round of numbered questions, each with a recommended answer, then wait. This is the one place where proceeding on assumptions is wrong. It needs the user, so it is never part of an unattended run.
- **A term is settled →** write it to `GLOSSARY.md` at once. `SPEC.md` §2 already names Person, Event, Photo and History: a glossary entry must agree with it, or `SPEC.md` is corrected in the same edit. From then on code, tests, CLI help and docs use the glossary's word.
- **A decision passes all three gates →** an ADR. Never into `DECISIONS.md`.
- **Everything else that was decided →** into `SPEC.md` before the session ends, marked **[S]** with the date, replacing the **[A]** or **[?]** it settles. Keep exact answers exact (numbers, orderings, "never"). Upstream this step is `/to-spec`, which publishes a GitHub issue; here `SPEC.md` is the spec, and nothing is written to the issue tracker unless the user asks.
- Scenarios and glossary examples use invented people only (the repository is public).
- **Before saying the session is done:** `git status` must show the edits to `GLOSSARY.md` / `SPEC.md` / `docs/adr/` that the session produced, and the user confirms the shared understanding. Then build test-first as described above.

Use only the skills in `.claude/skills/`. Do not use a skill or plugin from outside the repository, also when one is available in the session. The built-in commands of Claude Code (`/init`, `/loop`, `/code-review` and so on) are allowed.

| `tdd` | detail for the TDD workflow: good tests, seams, anti-patterns |
| `two-axis-review` | review a diff against the repo standards and against the spec |

| `swiftui-pro` | Paul Hudson's SwiftUI rules: API, views, data flow, navigation, design, accessibility, performance |
| `swiftdata-pro` | Paul Hudson's SwiftData rules: models, predicates, CloudKit, indexing |

- Start Claude Code with `scripts/claude.sh`. It loads the settings of the repository only, so plugins, skills, hooks and settings from `~/.claude` stay out. The personal `~/.claude/CLAUDE.md` and the memory of the project are still read. Only this script gives the full effect. For a session started with plain `claude`, `.claude/settings.json` switches off five plugins that overlap with the skills of the repository; other plugins and personal skills stay active there.
- `.claude/skills/README.md` gives the source and version of each skill. The copies stay unchanged; rules that adapt a skill to pplz belong in this file.
- Where a skill and this file disagree, this file wins. Known differences: `tdd` puts refactoring into the review stage, here a small cleanup directly after green is part of the cycle. `tdd` asks the user to confirm the seams before each test; here, agree the seams one time for a change, and state them when the user is away. `tdd` allows mocks at system boundaries; pplz tests use real stores in temporary files and no mocks or fakes without the user's permission. Where `tdd` says `code-review`, use `two-axis-review`. Where `autonomous` says `docs/agents/issue-tracker.md`, use "Issue tracker" below. `autonomous` names skills of the `spec` plugin (`/spec:*`); these are not in the repository, so use the fallback that the skill describes. Where it says `/spec:adversarial-code-review`, use `two-axis-review`. `tdd` names `codebase-design`, which is not in the repository: skip that step. The four Swift skills name each other by GitHub address: use the copy in `.claude/skills/`, and do not install a skill.
- `two-axis-review` reads commits only (`<fixed point>...HEAD`) and does not look for defects. For changes that are not committed, and to find defects, use the built-in `/code-review`.
- `DECISIONS.md`: the user sets each `Status`. `/spec:archive` and `/spec:overview` are not in the repository, so run the review flow of `.claude/skills/autonomous/decisions-format.md` when the user asks for it.
- Load `swiftui-pro` before you write or review code in `Sources/PplzUI` or `App/`, and read the reference files for the area you change. Its limits here: the deployment targets are macOS 15 and iOS 18, so an API of a later release needs `#available` and a fallback; the Swift language mode stays 6.0; UIKit and AppKit stay where the code uses them today (camera, share extensions, system contact card, the map in `PersonMap.swift`). During a feature or a fix, report its other findings as suggestions and do not apply them.
- Load the skill for the area before you write or review code: `swiftdata-pro` for `Model.swift`, `PplzStore.swift` and each query; `swift-concurrency-pro` for code with `async`, actors or tasks; `swift-testing-pro` for `Tests/`. The limits of `swiftui-pro` above apply to all three. More limits:
  - All four: new code follows the file layout that exists (some files hold more than one type, folders are the targets). Do not split a file or move a type because a skill says so.
  - All four: no protocol, mock or fake only to make code testable, without the user's permission. This applies to each skill, also where it recommends an injected dependency.
  - `swift-concurrency-pro`: pplz does not enable `NonisolatedNonsendingByDefault`. A `nonisolated` async function leaves the actor of its caller, as before Swift 6.2; ignore the rules of the skill that assume the opposite. Grand Central Dispatch stays where the code uses it for framework interop; here this skill wins over the "never" of `swiftui-pro`.
  - `swiftdata-pro`: the CloudKit rules in "Store" win. The skill recommends a versioned migration schema, and pplz has none: report that as a suggestion, and do not add one without the user's decision. Its class inheritance reference needs iOS 26 and does not apply.
  - `swift-testing-pro`: it recommends mocks for the network layer. pplz tests use no mocks or fakes without the user's permission. UI tests in `App/UITests` stay XCTest. Each suite keeps its `@Suite`. Do not change a test that exists only to satisfy a rule of the skill.
- For `two-axis-review`, the spec source is the GitHub issue named in the commits, else the section of `SPEC.md` for the area. The standards sources are this file and `docs/agents/domain.md`.

## Working guidelines

From [andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md). They bias toward caution over speed; for trivial tasks, use judgment. Where the user's own instructions say to proceed on reasonable assumptions instead of asking, those win.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
